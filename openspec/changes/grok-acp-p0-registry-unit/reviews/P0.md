## Findings

Severity: **S1** blocker, **S2** major, **S3** minor, **S4** nit.

### 1. S1 — `npm run lint` is broken by the Go 1.27.1 bump

`package.json` runs golangci-lint via `go run …/golangci-lint@v2.13.2`. Built that way, the linter's
language version is its own module's `go` directive (`go 1.26.0` for v2.13.2), and golangci-lint
refuses to analyze a module targeting a newer language version:

```
Error: can't load config: the Go language version (go1.26) used to build golangci-lint is lower than the targeted Go version (1.27.1)
```

This is a regression, not a pre-existing condition. I ran the same command on the `main` baseline
(`backend/go.mod` `go 1.25.7`, pin `v2.12.2`, whose module directive is `go 1.25.0`) and got
`0 issues.`; on this branch the command aborts with exit status 3. The comparison is minor-version
based, so `1.25.0` vs `1.25.7` is fine while `1.26` vs `1.27.1` is fatal.

The PR comment in `.github/workflows/go.yml` states that "v2.13.2 is built with go1.27". That is
true of the *published release binary* (`built with go1.27.0`, and it reports `0 issues.` on this
tree), which is why the CI job still passes — the action downloads that binary. It is not true of the
`go run` path that `package.json` and `AGENTS.md` document, so CI and the local loop now disagree.

Picking a newer pin does not fix this: v2.13.2 is the newest release, and no golangci-lint release
yet declares `go 1.27` in its own `go.mod`. Resolution options: keep `backend/go.mod` on a language
version golangci-lint can be built for, or change `npm run lint` to consume the released binary
instead of `go run`. Either way, `AGENTS.md` and `docs/development.md` must describe a command that
actually runs.

### 2. S1 — `validateTurnSettings` rejects every Grok model ID AO itself discovers

`grokacp.validateTurnSettings` requires `provider/model` and its comment asserts "Grok parses model
overrides as provider/model". The repository's own Grok evidence contradicts that:

- `internal/adapters/agent/grok/grok.go` passes bare names through the same `--model` flag; its test
  asserts `{"grok", "--no-auto-update", "--model", "grok-code-fast"}`.
- `internal/adapters/agent/modelcatalog/catalog.go` populates AO's Grok catalog from `grok models`;
  `TestParseGrokModelsIgnoresAuthAndDefaultStatus` expects the ID `grok-4.5`.
- Upstream (docs.x.ai CLI reference, agent-mode docs) documents `-m, --model <MODEL>` as "Model ID to
  use", example `grok-build`. No `provider/` prefix appears anywhere in Grok's documentation.

So a user who selects a model from AO's own Grok catalog, or carries a model override from an
existing Grok TUI session, gets `ErrChatConfigOptionInvalid` and cannot start the Chat turn — while
the PR's "valid" fixture `xai/grok-code-fast-1` is not a documented Grok model ID at all. The
validator inverts the intended outcome: it blocks the real IDs and admits synthetic ones.

Note the shared ACP layer already protects the user here. `acp/conversation.go` resolves a requested
model against the agent-advertised `model` choices and returns `ErrChatConfigOptionInvalid: ACP
session model does not offer %q` when it is unknown. A Grok-specific *format* gate therefore adds no
protection and only subtracts valid input.

This also means the OPSX spec is wrong, not just the code: `specs/chat-drivers/spec.md` mandates
"Requirement: Model Override Validation" with the scenario that `grok-3` must fail. Fix the spec
(drop the format requirement, or restate it as "reject nothing locally; let the advertised catalog
answer") in the same change as the code.

### 3. S2 — `--no-auto-update` placement after `agent` is unverified and may abort startup

`configure` emits `agent --no-auto-update … stdio`. Upstream documents this flag in global position
(`grok --no-auto-update -p "..."`), the AO TUI adapter also uses global position
(`grok --no-auto-update …`), and the agent-mode flag table lists only `-m/--model`,
`--always-approve`, `--reauth`, `--agent-profile`, and `--leader/--no-leader` as options accepted
between `agent` and the transport name. If the flag is not declared global in Grok's CLI parser, the
process exits on argv parse and every Chat session fails to launch. P0 waives live verification, so
nothing in this PR can detect that. This is cheap to de-risk now by matching the TUI adapter and the
documented example (`grok --no-auto-update agent … stdio`); otherwise it must be an explicit,
blocking P1 live-gate item.

### 4. S2 — Grok ACP session-mode IDs are assumed, not verified

`sessionMode` returns `acceptEdits` / `auto` / `bypassPermissions` on the stated assumption that
Grok's ACP mode IDs equal its TUI `--permission-mode` values. Those values are themselves not in
Grok's published flag list, and ACP mode IDs come from the agent's `session/new` mode state. If they
differ, `acp/conversation.go` fails the turn (`set ACP session mode %q` / `ErrACPSetterUnsupported`)
rather than degrading — so a wrong ID is a per-turn hard error for any session that sets an approval
mode. Acceptable to carry into P1 only if P1 explicitly asserts the advertised mode IDs against a
real `grok agent stdio` handshake and this file records that the mapping is unverified.

### 5. S3 — Unscoped toolchain migration bundled into a driver PR

Nothing in this OPSX change asks for Go 1.27.1, mise, a golangci-lint bump, or a Docker base-image
change; `proposal.md`/`tasks.md` name only the `grokacp` package and the registry, and the G2 gate
still reads "golangci-lint v2.12.2". `AGENTS.md` asks for surgical changes and one issue per PR. The
bundling is what produced finding 1, and it leaves the change's own gate description stale. Either
split the toolchain work into its own PR or update `proposal.md`/`tasks.md`/`design.md` gates to the
versions actually shipped.

### 6. S3 — Dev environment regresses for nix + direnv contributors

`flake.nix` drops `pkgs.go_1_25` and the `GOROOT` export without adding `pkgs.mise`, so
`nix develop` now yields a shell with no Go toolchain. `.envrc` gains `use mise`, which upstream mise
documentation marks "deprecated and no longer supported" and which only works after each developer
runs `mise direnv activate > ~/.config/direnv/lib/use_mise.sh`; without that file direnv fails to
load `.envrc` at all, taking the pre-existing `use flake` line down with it. mise's own docs
discourage combining mise with direnv. Add mise to the flake inputs (or keep a pinned Go there), and
document the required one-time setup.

### 7. S3 — Documentation left claiming Go 1.25.7

The PR updates the golangci-lint row of `docs/development.md` but not the Go rows in the same file
(prerequisites table "Go 1.25.7", the `go.mod requires go >= 1.25` troubleshooting row, and the
"match CI (Go 1.25.7+…)" note), nor `docs/stack.md` ("Backend language | Go 1.25.7 | … Matches
`backend/go.mod`"). mise is not mentioned in any doc even though it is now the pinned local
toolchain source. Per `docs/documentation-map.md` these are contract-layer artifacts, so the drift
matters.

### 8. S4 — `mise.toml` duplicates the version it claims to unify

The file comment says "there is one source of truth for the Go version", but `go = "1.27.1"` is a
second hardcoded pin next to `backend/go.mod`, with no CI check that they agree. mise can read
`go.mod` as an idiomatic version file (opt-in via `idiomatic_version_file_enable_tools go`), which
would make the comment true.

### 9. S4 — `cloud/go.mod` bumped without need

`go.work` only requires the workspace directive to be at least the highest module directive, so
`cloud` could have stayed at `go 1.26.5`. Raising it lifts that module's minimum toolchain for no
stated reason and widens the blast radius of an already out-of-scope change.

### 10. S4 — One spec-listed configure case is untested

`tasks.md` and `specs/chat-drivers/spec.md` require a configure case for
`ports.PermissionModeAuto` (no `--always-approve`). The table test covers defaults, `acceptEdits`,
bypass, model, model+bypass, and blank model; `auto` appears only in the `sessionMode` test. One
table row closes the gap.

## Verified as correct (for the record)

- **No credential injection.** `configure` returns a nil env overlay, and `grok.Plugin` does not
  implement `AugmentRuntimeEnv`, so `nativeacp` merges nothing extra: no `GROK_HOME`, no
  `XAI_API_KEY`, Chat and TUI share one Grok profile. `TestConfigureAddsNoEnvironmentOverlay` pins it.
- **Thin binding.** `New` delegates to `nativeacp.New` with the existing `agent/grok` plugin; no
  binary search, no download path, no auth logic of its own. Probe/auth delegation is asserted, and
  `TestRejectsBareModelNameBeforeResolvingBinary` proves validation runs before binary resolution on
  both `Start` and `Resume`.
- **`agent … stdio` shape.** Upstream confirms `grok agent stdio` and `--always-approve`, and that
  agent options belong between `agent` and the transport name — matching the emitted argv order
  (subject to finding 3).
- **Registration is complete and consistent.** `registry.Build` and `TestShippedChatDrivers` both
  include `HarnessGrok`; the neighbouring comments were updated. `settings.ChatHarnesses` derives
  from `SupportsChat`, so no second list needed touching.
- **No silent handoff enablement.** TUI↔Chat switching stays gated by the `AgentInterfaceHandoff`
  capability, so registering a Chat driver does not enable an unproven Grok handoff.
- **Scope is clean of P1–P4.** No live probe, no Playwright/desktop E2E, no SessionMeta work; the
  shared `acp`, `nativeacp`, and `persistenthost` packages are untouched, and their suites still pass.
